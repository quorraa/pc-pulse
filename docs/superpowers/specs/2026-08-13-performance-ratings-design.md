# Performance ratings: learning what "acceptable" means

**Date:** 2026-08-13
**Status:** Approved pending user review
**Builds on:** 2026-08-12-alert-calibration-design.md (incident lifecycle,
quality layer, durable baselines — all shipped by that spec's plan)

## Summary

After the 24-hour learning period, the machine baseline knows what the
machine *does* — not what the user considers *acceptable*. Workloads also
change: a baseline learned under last month's usage says nothing about
whether today's different behavior is fine. This feature adds a user
feedback loop: a quick in-app rating of overall performance, stored with
the demand context and a machine-generated performance digest, used to
calibrate the notification policy — and explicitly **never** to rewrite
the measured baselines.

The guiding hazard, named by the user: performance can feel deceptively
good under light use while the machine has actually degraded relative to
what it used to deliver under demanding load. Therefore a rating is only
ever interpreted inside its own demand context. "Fine at idle" teaches
nothing about "fine under load."

Ratings also feed forward: each one snapshots an agent-ready performance
digest, accumulating labeled training material for the optimization agent
planned as a future feature.

## The rating

`RatingVerdict`: `good | acceptable | sluggish` (three levels — each maps
to a distinct policy action; finer scales invite noise).

A `Rating` record (SQLite `ratings` table, camelCase JSON payload):

| Field | Content |
| --- | --- |
| id | uuid |
| at_ms | timestamp |
| verdict | good / acceptable / sluggish |
| demand | the demand bucket at rating time (below) |
| demand_detail | the raw composite inputs behind the bucket (CPU %, memory occupancy %, disk latency, IO rate — each as value and as percentile against the machine baseline) |
| digest | machine-generated performance digest (below) |
| open_incidents | fingerprints + severity + notify state of incidents active at rating time |

**Demand bucket**: `light | moderate | heavy`, derived by the service at
rating time from the trailing 10 minutes: composite = max of (CPU %
percentile, memory-occupancy percentile, IO percentile) against the
machine baseline sketches. ≥ p90 sustained ⇒ heavy; ≥ p50 ⇒ moderate;
else light. Derivation is service-side and tested; the bucket is stored,
not recomputed, so later reinterpretation cannot silently rebucket old
ratings.

**Performance digest**: generated by the service when the rating arrives,
using the same machinery as the analyzer's evidence bundle (system rollup
percentiles over the trailing hour, top processes by pressure score with
redacted paths, active incidents with quality scores, learning state,
collector health). Compact (≤ 32 KB), fully redacted like agent-context,
stored inside the rating row. This is the labeled corpus the future
optimization agent consumes: (verdict, demand, digest) triples.

Retention: ratings are small and precious (user labor) — never pruned by
the time-based retention job; capped at 1,000 rows LRU as a safety bound.

## UX

- **Hotkey `f`** ("how does it feel?") in Normal mode opens a three-choice
  overlay: `g` good · `a` acceptable · `s` sluggish · Esc cancels. One
  keypress to open, one to answer. Confirmation lands in the statusline.
- **Nudge**: a statusline message ("rate how this machine feels — press f"),
  never a modal, shown at most once per day, and only when BOTH: (a) the
  trailing hour contained ≥ 10 minutes in the heavy bucket — demanding-load
  labels are the valuable ones and the whole point; and (b) the learning
  period is over. Dismissed by any keypress (ordinary statusline turnover).
  Nudge state (last-nudged) persists in client prefs.
- Ratings appear in the Incidents page history region (or the detail pane
  of the day) as small annotations — visible, not centerpiece.

## Influence: notification policy only

Ratings adjust per **(alert kind, demand bucket)** notify-floor offsets —
never baselines, never detector thresholds, never severities:

- **False-positive signal** — a `good`/`acceptable` rating while one or
  more incidents were actively notifying (notify true, not acknowledged):
  each such incident's (kind, bucket) offset moves +0.05 toward stricter
  (higher effective confidence/persistence floors for notification of
  that kind in that bucket).
- **False-negative signal** — a `sluggish` rating with zero notifying
  incidents: all (kind, bucket) offsets for that bucket move −0.05 toward
  more permissive, AND the rating is flagged `unexplained: true` — an
  explicit signal for the analyzer/optimization agent that the detectors
  missed something the user felt.
- **Confirmation** — `sluggish` while incidents were notifying: offsets
  unchanged (the system was right); the rating still records everything.
- Offsets are bounded to ±0.15 total, decay with a 30-day half-life
  (applied lazily at read time from the rating history — the ratings table
  is the single source of truth; no second mutable store), and are applied
  inside `quality::decide` as an additive term on the confidence and
  persistence floors for that (kind, bucket).
- The current effective offsets are visible in the agent context and in
  the Incidents detail pane for affected kinds ("policy adjusted by your
  ratings: +0.05").

**Deceptive-comfort guard (the user's core requirement):** offsets are
keyed by demand bucket, and a rating only ever touches its own bucket's
offsets. A month of `good` ratings at idle leaves the heavy bucket's
policy exactly as strict as the day it shipped. Pinned by a dedicated
test.

**Learning-period interaction:** ratings during the learning period are
stored (with `during_learning: true`) but produce no offsets — the policy
they would adjust is not yet in effect.

## Protocol

Two additive pipe requests: `AddRating { verdict }` (client sends only
the verdict; the service owns context and digest because the data lives
there) returning the stored record, and `GetRatings { limit }` for the
UI/history. `PROTOCOL_VERSION` stays 1; old clients simply never send
them.

## Out of scope

- The optimization agent itself (future feature; this spec only produces
  its labeled corpus).
- Any baseline or detector-threshold modification from ratings.
- Per-bucket machine baselines (a possible future refinement of the same
  hazard; the rating bucketing carries the intent for now).
- Rating editing/deletion UI; cross-machine aggregation; new TUNE rows.

## Tests

1. Demand-bucket derivation against seeded baseline sketches (light /
   moderate / heavy boundaries, sustained requirement).
2. Nudge gating: no nudge during learning, none without a heavy stretch,
   at most one per day, prefs-persisted.
3. False-positive path: `good` during a notifying collector-budget
   incident raises that (kind, bucket) offset by 0.05, capped at +0.15.
4. False-negative path: `sluggish` with nothing notifying lowers the
   bucket's offsets and stores `unexplained: true`.
5. Deceptive-comfort: repeated `good` at light never changes heavy-bucket
   offsets; a heavy-bucket `sluggish` still notifies at full sensitivity.
6. Decay: an offset from a 60-day-old rating contributes a quarter weight.
7. Digest: redaction matches agent-context rules; size bound; contains
   rollup + incidents + learning state; round-trips through SQLite.
8. Compat: old client against new service (no rating requests, nothing
   changes); pre-upgrade database gains the ratings table via tolerant
   migration.
